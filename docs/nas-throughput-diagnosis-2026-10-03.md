# NAS 補抓緩慢與資料不足診斷（2026-10-03）

檢查時間：2026-10-03 18:48–18:54，Asia/Taipei。目標來源日為 2026-10-02。
檢查方式：NAS HTTP GET、SSH 讀取執行狀態、PostgreSQL SELECT／EXPLAIN ANALYZE，以及本機記憶體資料庫重現。
以下第 1–5 節記錄最初唯讀診斷；後續修正與部署驗證見文末。
診斷時 NAS 部署版本：`215a2a956ffafab174dbd41fd6dafc818734a6a8`。

## 結論

Worker 有持續進度，但佇列反覆優先處理全空股票、每檔強制重抓完整歷史窗口，加上來源筆數計數的昂貴查詢，使實際新增覆蓋率非常低。另有全市場股票清單更新的外鍵錯誤，以及首頁把尚無新版數值評分的股票統一算成資料不足，共同造成畫面長時間停留在兩千多檔。

## 1. 約 80% 請求花在全空股票，其他股票難以輪到

以 13:00 至 18:52 左右已結束的單股作業統計：

| 回應情況 | 作業次數 | 不同股票 | 資料 HTTP 請求 |
| --- | ---: | ---: | ---: |
| 五項來源 rows_received 合計為 0 | 577 | 116 | 13,848 |
| 至少一項來源有回傳資料 | 145 | 145 | 3,479 |
| 合計 | 722 | 261 | 17,327 |

全空作業消耗 79.92% 資料請求。此為作業紀錄的 rows_received 定義，不把「已有資料但未新增版本」誤算成全空。當時另有一檔進行中，因此含進行中的統計為 723 次、262 檔。

例如 1230、1258、1262、1311 今天已各嘗試 6 次。1230、1258 在 13、14、15、17、18 點輪次都重抓 20 天分點，且分點回傳 0 筆。

原因在 `backend/app/refresh_queue.py:24` 的 `_universe_budget_queue`：

- 先排完全沒有來源資料且沒有數值評分的股票。
- 接著依來源資料的 `fetched_at` 排序，沒有使用成功或失敗的補抓嘗試時間輪替。
- 全空回應不會新增來源資料，這些股票每輪仍排最前。13:00 以後的五輪第一檔都是 1230，其 `ordered_latest_fetch_at` 為空。
- 本輪的 `deferred_stock_ids` 可避免同輪重試，但新輪會重建，不能避免跨輪持續搶占。
- 同一目標交易日不重複累計排除次數是現有規則；1230、1258 的 `no_data_attempts` 均為 1。不能靠同日多跑幾輪讓它們達到五個交易日的排除門檻。

10:12 的部署稽核作業 33636 曾清除 2,100 筆缺資料計次，解除 1,645 檔既有排除。這使大量待查股票重新入列；真正問題是入列後缺少公平輪替，不能將清零本身當成應撤銷的操作。

## 2. 3,500 是每輪 HTTP 上限，完整一檔通常花 24 次

`backend/app/ingestion.py:1444` 對自動與手動批次都呼叫 `force_refresh=True`。單股計畫通常包括法人、外資持股、價格、持股分布各 1 次，再加分點逐交易日 20 次，即 24 次。

因此 `floor(3500 / 24) = 145`，與 NAS 多輪實際完成 145 檔吻合。這裡「完成」指完成該檔嘗試，不保證取得數值評分。

`backend/app/finmind.py:722` 的分點抓取會在 `retry_deferred` 或 `force_refresh` 時清空本次 completed 集合。自動佇列也未啟用 `reuse_broker_observations`，已存在的完整分點歷史仍可能重抓。即使只缺一日法人資料，也照樣跑五項來源。

## 3. 寫入前後全來源 COUNT 是可重現的效能瓶頸

`backend/app/ingestion.py:976`、`:978` 的單股 sink，每次接收資料都對 `source_revisions` 同 dataset 做兩次 `COUNT(*)`，用前後差計算新增版本數。

NAS 執行一次下列唯讀查詢的 EXPLAIN ANALYZE：

```sql
SELECT count(*)
FROM source_revisions
WHERE dataset = 'TaiwanStockTradingDailyReport';
```

- 執行時間：4,060.405 ms。
- Parallel Index Only Scan：每 loop 平均 9,456,365 rows，3 loops，約 28,369,095 rows。
- Shared read blocks：527,616；heap fetches：4,966,206。
- Shared read blocks 是 PostgreSQL 緩衝層讀取量，不能直接當成實體磁碟流量。

有資料的 20 個分點日可觸發最多 40 次這類計數，另有其他來源、逐筆 upsert、checkpoint 與評分成本。單次測量受快取與當時負載影響，不能將 4 秒固定套用到每次呼叫，但已足以證明全來源反覆計數是應移除的重工。

當時 worker 與 PostgreSQL 各約 50% CPU，NAS 另有三個 stock-v3 容器各約 100% CPU。共享負載可能加劇延遲，但未停止其他服務，也不將它們認定為主要根因。

## 4. 股票清單更新有外鍵錯誤，拖累全市場同步

最新兩筆 TaiwanStockInfo 失敗紀錄（31763、32528）均包含：

```text
ForeignKeyViolation: source_revisions_stock_id_fkey
Key (stock_id)=(7812) is not present in table stocks.
```

`TaiwanStockInfo` 最後一次 SUCCESS 是 2026-09-02 21:11。9 月 4 日起共查得 15 次 `gkpj` 錯誤紀錄；`gkpj` 是包裝後的 SQLAlchemy 錯誤代碼，最新樣本的底層原因為上述外鍵違反，不能把它解讀為 FinMind 額度或權限錯誤。

`backend/app/ingestion.py:321` 先 `_record_revision` 再 `_upsert(Stock)`；`backend/app/db.py:18` 使用 `autoflush=False`，新增股票與 revision 的寫入順序未被正確保障。本機以開啟 SQLite foreign_keys 的記憶體資料庫、同樣的 autoflush 設定呼叫 `ingest_records` 新增 7812，成功重現 `FOREIGN KEY constraint failed`，未碰 NAS 資料。

`backend/app/ingestion.py:2137` 在 universe 更新失敗後清空 required source 計畫，後續分點也會 DEFERRED。這說明為何逐股補抓仍在進行，但全市場狀態長時間未正常更新。不能直接把全市場 data_sync_status 的舊日期當成每檔實際資料日期。

## 5. 首頁 2,047 檔混合了未有新版評分與已評估不足

約 18:52 的資料庫與 API 交叉檢查：

| 狀態 | 檔數 |
| --- | ---: |
| 普通股總數 | 2,148 |
| 有新版數值評分 | 101 |
| 有新版評估但缺資料 | 252 |
| 尚無新版評分紀錄 | 1,795 |
| 首頁資料不足 = 252 + 1,795 | 2,047 |

新版 `s-only-v6-calendar-v2` 的最早評分為今天 10:20。`backend/app/main.py:770` 先把全 universe 預設為 DATA_INSUFFICIENT，再以目前版本的數值結果覆蓋，所以畫面不是已實際檢查完 2,047 檔的缺口計數。舊版本最新評估也全為 DATA_INSUFFICIENT；不能宣稱只是切換版本讓原本全部正常的分數消失。

已評估不足的 252 檔均包含 missing_institutional，部分也缺其他來源。例如 8472 其他四項評分來源已齊，法人缺 2026-09-21，仍無法取得完整 20 日評分。單靠相同窗口不斷重抓不保證消除這類缺口，也不能直接把缺列補成零。

18:00 輪開始時，真正達成 10/02 全部每日完成條件的為 86 檔；13:00 輪結束為 78 檔。101 檔有數值評分與 86 檔每日完成的定義不同，前者可包含較早日期 fallback，後者還要求目標日期與來源寫入時間條件。

## 建議修正順序與驗收

1. 修正無資料股票的跨輪公平性：持久化 attempt 時間／目標日、為已證實全空來源安排合理重試時間，先讓尚未嘗試的股票取得處理機會；保留五個不同交易日才排除的規則。
2. 自動補抓採缺口更新，保留已驗證的分點日；對已齊資料但尚無新版評分者先做本機評分。手動強制刷新語意可以保留。
3. 改由寫入流程直接回傳新增版本數，移除 sink 的全 dataset COUNT；驗收每檔耗時與 SQL 執行次數。
4. 新增股票先完成主表 flush，再寫 revision，整批維持同一交易；以開啟外鍵的資料庫測試新股與 rollback。
5. 在來源與公平性修正後，從 PostgreSQL 補跑目前版本全 universe 評分；畫面另列「待新版評分」、「已評估資料不足」及來源原因，不以放寬資料完整性降低數字。

驗收應同時看每輪不同股票數、新增可評分檔數、全空重複請求比例、p50/p95 每檔時間、universe 同步成功與每日完成數，不能只看 3,500 是否耗盡或 job 是否 SUCCESS。
